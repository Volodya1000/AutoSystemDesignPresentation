# AutoSystemDesignPresentation

Техническая презентация AutoSystemDesign для коллег и системных архитекторов. Основная задача — показать **идеи проектирования и способы проверки модели**, а не только итоговые картинки.

## Структура презентации

В презентации **16 слайдов**:

1. Постановка задачи: BRD → проверяемая архитектурная модель.
2. Пример BRD интернет-магазина, преобразование исходных цитат в требования и обнаружение противоречия.
3. Проверка соответствия извлечённых требований исходным цитатам BRD.
4. Схема стадий BRD → C4 → расчёт производительности / диаграммы последовательностей → API.
5. Структурированная модель компонентов, проверки и повторная генерация при ошибках.
6. Доменные типы C4, допустимые связи, семантические валидаторы и протоколы.
7. Отдельные примеры C4 и диаграммы последовательностей.
8. REST API с примером OpenAPI JSON на одном слайде и отдельная иллюстрация Swagger UI.
9. Проверка производительности на основе теории массового обслуживания и векторное представление расчётного отчёта.

### Почему часть иллюстраций пока не из одного запуска

**BRD и извлечённые требования** образуют единый демонстрационный пример интернет-магазина. Текст на слайде требований является сокращённым пояснением, **не логом реального LLM-запуска**.

Слайды C4, Sequence и Swagger пока используют существующие изображения из репозитория. Фрагмент OpenAPI JSON иллюстративный, а не выгруженный из конвейера документ.

Слайд анализа производительности воспроизводит данные из **предоставленного отчёта `checkout_baseline_performance_analysis.pdf`**, где для узлов рассчитаны 60 RPS, а максимальная оценка средней задержки синхронного пути равна 32,10 мс. Это другой прогон. **Нельзя** выдавать эту цифру за проверку p95/p99 или за результат указанного BRD.

До демонстрации единого прогона эти различия должны быть явно обозначены, а не замаскированы похожими названиями.

## План замены примеров после локального запуска

| Слайд | Что заменить | Источник |
| --- | --- | --- |
| BRD | Финальное изложение требований | Один выбранный документ заказчика |
| Извлечённые требования | Реальный набор требований и подтверждающих цитат | Результат извлечения этого BRD |
| C4 | `images/c4_example_2.png` | Диаграмма этого же сценария |
| Sequence | `images/sequence_example_3.png` | Диаграмма соответствующего функционального требования |
| Swagger | `images/swagger_example_2.png` | Swagger UI из той же API-спецификации |
| OpenAPI JSON | Иллюстративный код на слайде | Отрывок сгенерированного OpenAPI |
| Отчёт | Векторная таблица в `presentation.tex` | Показатели из PDF этого же набора требований |

После подмены изображений желательно сохранить одинаковые идентификаторы требований и компонентов между BRD, C4, Sequence, OpenAPI и анализом.

## Компиляция

Потребуется LuaLaTeX, Beamer и DejaVu Sans / DejaVu Sans Mono.

```bash
lualatex -interaction=nonstopmode -halt-on-error presentation.tex
lualatex -interaction=nonstopmode -halt-on-error presentation.tex
```

GitHub Actions выполняет сборку на pull request и push в `main`. PDF публикуется как артефакт, а в PR из этого репозитория также автоматически коммитится в ветку.

## Что важно не заявлять без доказательств

- Буквальное наличие цитаты подтверждает происхождение значения из BRD, но само по себе не доказывает правильность семантической классификации.
- Численная оценка среднего времени не подтверждает процентильный SLA.
- Аналитические модели очередей не заменяют нагрузочные испытания и не гарантируют поведение реальной системы.
- Образцы результатов из разных запусков нельзя представлять как артефакты единого BRD.
