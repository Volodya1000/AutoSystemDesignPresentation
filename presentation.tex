\begin{frame}{Возможности инструмента}

\begin{columns}[T,onlytextwidth]
  \column{0.48\textwidth}
  \textbf{Построение архитектуры}
  \begin{itemize}
    \item Формирование архитектурной модели по функциональным и нефункциональным требованиям.
    \item Генерация диаграмм компонентов и последовательностей.
    \item Формирование спецификации API.
  \end{itemize}

  \column{0.48\textwidth}
  \textbf{Проверка и анализ}
  \begin{itemize}
    \item Проверка структуры и связей архитектурной модели.
    \item Расчётная оценка нагрузки и задержек.
    \item Извлечение требований из документа с цитатами, подтверждающими исходный текст.
  \end{itemize}
\end{columns}

\vfill
\textcolor{Muted}{Результаты формируются в виде архитектурных моделей и связанных с ними артефактов.}

\begin{frame}{Проверка достоверности извлечённых данных}

\begin{columns}[T,onlytextwidth]
  \column{0.48\textwidth}
  \textbf{Правила проверки}
  \begin{itemize}
    \item Каждая цитата должна присутствовать в исходном тексте.
    \item Значения полей сценария сопровождаются проверенными цитатами.
    \item Числа должны буквально встречаться в цитате: пересчёт единиц не выполняется.
  \end{itemize}

  \column{0.48\textwidth}
  \textbf{Если подтверждения нет}
  \begin{itemize}
    \item Неподтверждённые утверждения и значения исключаются с указанием причины.
    \item Неоднозначности и противоречия сохраняются для проверки человеком.
  \end{itemize}
\end{columns}

\vfill
\textcolor{Muted}{Для извлечённых значений сохраняются исходные цитаты и результаты проверки.}

\begin{frame}{Варианты сервера рендеринга PlantUML}

Для компиляции исходного кода PlantUML в изображение доступны три варианта:

\begin{enumerate}
  \item \textbf{Локальный сервер PlantUML, развёртываемый через Docker Compose}\\
  Развёртывается вместе с проектом; конфигурация включена в репозиторий.
  \item \textbf{Официальный сервер PlantUML}\\
  Используется размещённый разработчиками PlantUML сервер.
  \item \textbf{Kroki}\\
  Универсальный сервис рендеринга диаграмм, поддерживающий PlantUML и другие форматы.
\end{enumerate}

  {\footnotesize
  \begin{itemize}
    \item LiteLLM позволяет обращаться к разным моделям через OpenAI-совместимый API.
    \item LLM формирует структурированный вывод по классам доменной модели; код PlantUML она не пишет.
    \item Доменная модель описывает архитектуру, функциональные требования и спецификацию API.
    \item Сейчас диаграммы строятся через PlantUML. Структурированная модель позволяет добавить другой рендерер, например Mermaid, отдельно от генерации модели.
  \end{itemize}
  }

\begin{frame}{Повторная генерация при ошибках}

\begin{enumerate}
  \item LLM формирует структурированный ответ по классам доменной модели.
  \item Ответ разбирается как JSON и преобразуется в типизированные модели.
  \item При ошибке JSON-разбора в контекст добавляется описание ошибки.
  \item Если модель не проходит доменные валидаторы, в контекст добавляется форматированное описание нарушенных правил.
  \item LLM получает следующую попытку с учётом ошибки и исправляет ответ.
\end{enumerate}

\vspace{0.2cm}
\textbf{Число попыток ограничено настройкой.} Если лимит исчерпан,
генерация завершается ошибкой, а не запускается бесконечно.

\end{frame}

\begin{frame}{Модель архитектуры C4}

\begin{columns}[T,onlytextwidth]
  \column{0.30\textwidth}
  \textbf{Типы узлов}
  \begin{itemize}
    \item Клиент
    \item Балансировщик нагрузки
    \item Вычислительный узел
    \item База данных
    \item Кэш
    \item Брокер сообщений
  \end{itemize}

  \column{0.67\textwidth}
  \textbf{Параметры, задаваемые LLM}
  \begin{itemize}
    \item Число реплик, параллелизм и размер очереди
    \item Среднее и стандартное отклонение времени обработки
    \item Оценка месячной стоимости узла
  \end{itemize}

  \textbf{Использование параметров}
  \begin{itemize}
    \item Значения проверяются по типам и ограничениям доменной модели.
    \item Используются в расчётах пропускной способности, задержек и бюджета.
  \end{itemize}
\end{columns}

\vspace{0.10cm}
\textcolor{Muted}{Стоимость задаётся в модели, а не получается из актуального каталога облачного провайдера.}

\vfill

\end{frame}

\begin{frame}{Протоколы взаимодействия между узлами}

\begin{itemize}
  \item LLM выбирает протокол для каждой связи: HTTP (REST), gRPC, TCP или Message Queue.
  \item Протокол и признак асинхронности сохраняются в модели и отражаются на C4-диаграмме.
  \item При расчёте критического пути учитываются только синхронные связи; сетевая задержка берётся из отдельного параметра связи.
  \item Для диаграмм последовательностей валидатор проверяет, что события и уведомления отправляются асинхронно.
\end{itemize}

\vspace{0.15cm}
\textbf{Планируется добавить:} Webhooks, Long Polling, Server-Sent Events (SSE).

\end{frame}

% --------------------------------------------------
\begin{frame}{Реализованные валидаторы диаграммы компонентов}

\textbf{Структура графа}
\begin{itemize}
  \item У каждого узла уникальный идентификатор.
  \item Каждая связь соответствует разрешённой паре типов узлов.
  \item Граф не содержит циклов.
  \item Каждый узел связан хотя бы с одним другим узлом.
\end{itemize}

\end{frame}

% --------------------------------------------------
\begin{frame}{Реализованные валидаторы диаграммы компонентов}

\textbf{Валидация семантики}
\begin{itemize}
  \item Брокер сообщений должен быть связан с узлом-производителем и узлом-потребителем сообщений.
  \item При использовании кэша должен быть определён путь обращения к основному хранилищу при промахе кэша.
\end{itemize}

\textbf{Валидация на основе расчётов}
\begin{itemize}
  \item Рассчитывается загрузка узлов с ограниченной пропускной способностью с учётом RPS, числа реплик и параллелизма.
  \item Средняя задержка синхронного критического пути оценивается с учётом очередей и сетевых задержек и сравнивается с заданным порогом.
\end{itemize}

\end{frame}

\begin{frame}{Допущения и дальнейшее развитие анализа нагрузки}

\begin{columns}[T,onlytextwidth]
  \column{0.49\textwidth}
  \textbf{Текущая оценка}
  \begin{itemize}
    \item Поток распределяется поровну между клиентами и исходящими связями.
    \item Задержка оценивается аналитически по параметрам узлов и сетевым задержкам.
    \item Проверяется средняя задержка; p95/p99 и симуляция нагрузки пока не рассчитываются.
  \end{itemize}

  \column{0.49\textwidth}
  \textbf{Следующие направления}
  \begin{itemize}
    \item Развитие моделей очередей и каналов обслуживания.
    \item Отдельная проверка SLO по перцентилям.
    \item Симуляция нагрузки с помощью SimPy.
  \end{itemize}
\end{columns}

\end{frame}

% --------------------------------------------------
\begin{frame}{Реализованные валидаторы диаграммы последовательностей}

\textbf{Текущие правила}
\begin{itemize}
  \item На каждое функциональное требование — отдельная диаграмма.
  \item Ссылки на существующие роли и узлы C4.
  \item Соответствие сценария исходному требованию.
  \item Использование всех объявленных линий жизни.
  \item Разные бизнес-роли не используют один клиентский компонент.
  \item События и уведомления должны быть асинхронными.
\end{itemize}
