\begin{frame}{Цель}
\textbf{Разработать инструмент для автоматизированного построения
и проверки архитектурных моделей микросервисной системы на основе
функциональных и нефункциональных требований и заданного профиля
нагрузки.}
\end{frame}

% --------------------------------------------------
\begin{frame}{Входные данные и результаты}

\begin{columns}[T,onlytextwidth]
  \column{0.47\textwidth}
  {\bfseries\large Пользователь передаёт на вход:}
  \begin{itemize}
    \item BRD (документ бизнес-требований)
    \item Функциональные требования
    \item Нефункциональные требования
    \item Профиль нагрузки
  \end{itemize}

  \column{0.47\textwidth}
  {\bfseries\large Пользователь получает на выход:}
  \begin{itemize}
    \item C4 Component Diagram
    \item Sequence-диаграмма на каждое функциональное требование
    \item OpenAPI 3.1 и Swagger UI
  \end{itemize}
\end{columns}

\vfill
\textcolor{Muted}{Вход можно задать в YAML или передать документ BRD:
требования из документа извлекаются автоматически.}

\end{frame}

\begin{frame}{Модель архитектуры C4}

\textbf{Типы узлов}
\begin{itemize}
  \item Клиент, балансировщик нагрузки
  \item Вычислительный узел
  \item База данных, кэш, брокер сообщений
\end{itemize}

\vspace{0.20cm}
\textbf{Параметры модели}

Число реплик, параллелизм, время обработки, размер очереди,
стоимость компонентов и профиль запросов (RPS).

\vspace{0.20cm}
\textbf{Связи}

Разрешены только определённые пары типов узлов.
Для каждой связи задаётся протокол взаимодействия.

\begin{frame}{Валидаторы Sequence}

\textbf{Текущие правила}
\begin{itemize}
  \item На каждое функциональное требование — отдельная диаграмма.
  \item Ссылки на существующие роли и узлы C4.
  \item Соответствие сценария исходному требованию.
  \item Использование всех объявленных линий жизни.
  \item Разные бизнес-роли не используют один клиентский компонент.
  \item События и уведомления должны быть асинхронными.
\end{itemize}
