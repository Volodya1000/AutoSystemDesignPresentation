\begin{frame}{Варианты сервера рендеринга PlantUML}

Для компиляции исходного кода PlantUML в изображение доступны три варианта:

\begin{enumerate}
  \item \textbf{Локальный сервер PlantUML, развёртываемый через Docker Compose}\\
  Развёртывается вместе с проектом; конфигурация включена в репозиторий.
  \item \textbf{Официальный сервер PlantUML}\\
  Используется размещённый разработчиками PlantUML сервер.
  \item \textbf{Kroki}\\
  Универсальный сервис рендеринга диаграмм, поддерживающий PlantUML и другие форматы.
\end{enumerate}

\vfill
\begin{itemize}

  \item LLM формирует structured output по классам доменной модели; код PlantUML она не пишет.
  \item Доменная модель описывает архитектуру, функциональные требования и спецификацию API.
  \item Рендерер преобразует эту модель в диаграммы; его можно заменить или дополнить, например, Mermaid, без изменения доменной модели.

\begin{frame}{Валидаторы структуры графа}

\begin{itemize}
  \item \textbf{Уникальность узлов:} каждый узел имеет уникальный идентификатор.
  \item \textbf{Допустимость связей:} каждая связь соответствует разрешённой паре типов узлов.
  \item \textbf{Отсутствие циклов:} граф не содержит запрещённых циклических зависимостей.
  \item \textbf{Связность:} нет узлов, не связанных ни с одним другим узлом.
\end{itemize}

\vfill
\textcolor{Muted}{Эти проверки оценивают структуру графа и не заменяют проверку смысла взаимодействий.}

\end{frame}

% --------------------------------------------------
\begin{frame}{Валидация семантики и расчётов}

\textbf{Валидация семантики}
\begin{itemize}
  \item Брокер сообщений должен быть связан как минимум с узлом, отправляющим сообщения, и узлом, получающим сообщения.
  \item При использовании кэша должен быть определён путь обращения к основному хранилищу при промахе кэша.
\end{itemize}

\vspace{0.15cm}
\textbf{Валидация на основе расчётов}
\begin{itemize}
  \item Рассчитывается загрузка вычислительных узлов с учётом потока запросов, числа реплик и параллелизма.
  \item Оцениваются теоретическая задержка обработки и соблюдение заданного бюджета задержки.
\end{itemize}

\vfill
\textcolor{Muted}{Проверки выявляют заданные классы ошибок, но не доказывают корректность всей архитектуры.}

\end{frame}

% --------------------------------------------------
\begin{frame}{Протоколы взаимодействия между узлами}

Для каждой связи выбирается протокол из разрешённого набора.

\begin{itemize}
  \item \textbf{Синхронный запрос по HTTP (REST)} — узел отправляет запрос и ожидает ответ.
  \item \textbf{Синхронный вызов gRPC} — узел вызывает операцию другого узла и ожидает результат.
  \item \textbf{Подключение к базе данных по TCP} — узел обращается к хранилищу по сетевому протоколу базы данных.
  \item \textbf{Асинхронная очередь сообщений} — отправитель публикует сообщение, а получатель обрабатывает его независимо.
\end{itemize}

\vspace{0.2cm}
\textbf{Планируется добавить:} вебхуки, длительный опрос и потоковую передачу событий через SSE.

\vfill
\textcolor{Muted}{Для каждого протокола задано, является ли взаимодействие синхронным или асинхронным.}

\end{frame}

\begin{frame}{Реализованные валидаторы диаграммы последовательностей}

\textbf{Текущие правила}
\begin{itemize}
  \item На каждое функциональное требование — отдельная диаграмма.
  \item Ссылки на существующие роли и узлы C4.
  \item Соответствие сценария исходному требованию.
  \item Использование всех объявленных линий жизни.
  \item Разные бизнес-роли не используют один клиентский компонент.
  \item События и уведомления должны быть асинхронными.
\end{itemize}
