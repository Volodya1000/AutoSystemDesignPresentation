\begin{frame}{Проверка достоверности извлечённых данных}

\begin{columns}[T,onlytextwidth]
  \column{0.48\textwidth}
  \textbf{Правила проверки}
  \begin{itemize}
    \item Каждая цитата должна присутствовать в исходном тексте.
    \item Значения полей сценария сопровождаются проверенными цитатами.
    \item Числа должны буквально встречаться в цитате: пересчёт единиц не выполняется.
  \end{itemize}

  \column{0.48\textwidth}
  \textbf{Если подтверждения нет}
  \begin{itemize}
    \item Неподтверждённые утверждения и значения исключаются с указанием причины.
    \item Неоднозначности и противоречия сохраняются для проверки человеком.
  \end{itemize}
\end{columns}

\vfill
\textcolor{Muted}{Для извлечённых значений сохраняются исходные цитаты и результаты проверки.}

\begin{frame}{Варианты сервера рендеринга PlantUML}

Для компиляции исходного кода PlantUML в изображение доступны три варианта:

\begin{enumerate}
  \item \textbf{Локальный сервер PlantUML, развёртываемый через Docker Compose}\\
  Развёртывается вместе с проектом; конфигурация включена в репозиторий.
  \item \textbf{Официальный сервер PlantUML}\\
  Используется размещённый разработчиками PlantUML сервер.
  \item \textbf{Kroki}\\
  Универсальный сервис рендеринга диаграмм, поддерживающий PlantUML и другие форматы.
\end{enumerate}

    Рендеринг PlantUML в изображение

  \column{0.39\textwidth}
  \textbf{Ключевые принципы}
  {\footnotesize
  \begin{itemize}
    \item LiteLLM позволяет обращаться к разным моделям через OpenAI-совместимый API.
    \item LLM формирует структурированный вывод по классам доменной модели; код PlantUML она не пишет.
    \item Доменная модель описывает архитектуру, функциональные требования и спецификацию API.
    \item Рендерер преобразует эту модель в диаграммы; его можно заменить или дополнить, например, Mermaid, без изменения доменной модели.
  \end{itemize}
  }
\end{columns}

\end{frame}

\begin{frame}{Повторная генерация при ошибках}

\begin{enumerate}
  \item LLM формирует структурированный ответ по классам доменной модели.
  \item Ответ разбирается как JSON и преобразуется в типизированные модели.
  \item При ошибке JSON-разбора в контекст добавляется описание ошибки.
  \item Если модель не проходит доменные валидаторы, в контекст добавляется форматированное описание нарушенных правил.
  \item LLM получает следующую попытку с учётом ошибки и исправляет ответ.
\end{enumerate}

\vspace{0.2cm}
\textbf{Число попыток ограничено настройкой.} Если лимит исчерпан,
генерация завершается ошибкой, а не запускается бесконечно.

\end{frame}

\begin{frame}{Реализованные валидаторы диаграммы компонентов}

\textbf{Структура графа}
\begin{itemize}
  \item У каждого узла уникальный идентификатор.
  \item Каждая связь соответствует разрешённой паре типов узлов.
  \item Граф не содержит циклов.
  \item Каждый узел связан хотя бы с одним другим узлом.
\end{itemize}

\end{frame}

% --------------------------------------------------
\begin{frame}{Реализованные валидаторы диаграммы компонентов}

\textbf{Валидация семантики}
\begin{itemize}
  \item Брокер сообщений должен быть связан с узлом-производителем и узлом-потребителем сообщений.
  \item При использовании кэша должен быть определён путь обращения к основному хранилищу при промахе кэша.
\end{itemize}

\textbf{Валидация на основе расчётов}
\begin{itemize}
  \item Рассчитывается загрузка вычислительных узлов с учётом RPS, числа реплик и параллелизма.
  \item Оцениваются теоретическая задержка обработки и соблюдение заданного бюджета задержки.
\end{itemize}

\end{frame}

\begin{frame}{Реализованные валидаторы диаграммы последовательностей}

\textbf{Текущие правила}
\begin{itemize}
  \item На каждое функциональное требование — отдельная диаграмма.
  \item Ссылки на существующие роли и узлы C4.
  \item Соответствие сценария исходному требованию.
  \item Использование всех объявленных линий жизни.
  \item Разные бизнес-роли не используют один клиентский компонент.
  \item События и уведомления должны быть асинхронными.
\end{itemize}
