\begin{frame}{Возможности инструмента}
\begin{columns}[T,onlytextwidth]
\column{0.48\textwidth}\textbf{Построение архитектуры}
\begin{itemize}\item Формирование архитектурной модели по функциональным и нефункциональным требованиям.\item Генерация диаграмм компонентов и последовательностей.\item Формирование спецификации API.\end{itemize}
\column{0.48\textwidth}\textbf{Проверка и анализ}
\begin{itemize}\item Проверка структуры и связей архитектурной модели.\item Расчётная оценка нагрузки и задержек.\item Извлечение требований из документа с цитатами, подтверждающими исходный текст.\end{itemize}
\end{columns}\vfill\textcolor{Muted}{Результаты формируются в виде архитектурных моделей и связанных с ними артефактов.}

\begin{frame}{Проверка достоверности извлечённых данных}
\begin{columns}[T,onlytextwidth]
\column{0.48\textwidth}\textbf{Правила проверки}
\begin{itemize}\item Каждая цитата должна присутствовать в исходном тексте.\item Значения полей сценария сопровождаются проверенными цитатами.\item Числа должны буквально встречаться в цитате: пересчёт единиц не выполняется.\end{itemize}
\column{0.48\textwidth}\textbf{Если подтверждения нет}
\begin{itemize}\item Неподтверждённые утверждения и значения исключаются с указанием причины.\item Неоднозначности и противоречия сохраняются для проверки человеком.\end{itemize}
\end{columns}\vfill\textcolor{Muted}{Для извлечённых значений сохраняются исходные цитаты и результаты проверки.}
\end{frame}

\begin{frame}{Варианты сервера рендеринга PlantUML}
Для компиляции исходного кода PlantUML в изображение доступны три варианта:
\begin{enumerate}\item \textbf{Локальный сервер PlantUML, развёртываемый через Docker Compose}\\Развёртывается вместе с проектом; конфигурация включена в репозиторий.
\item \textbf{Официальный сервер PlantUML}\\Используется размещённый разработчиками PlantUML сервер.
\item \textbf{Kroki}\\Универсальный сервис рендеринга диаграмм, поддерживающий PlantUML и другие форматы.\end{enumerate}
\end{frame}

\begin{frame}{Генерация и проверка}
\begin{columns}[T,onlytextwidth]
\column{0.58\textwidth}\textbf{Конвейер генерации}\centering
\diagramimage[0.96\linewidth]{generation_pipeline.png}{Этапы генерации: требования, LLM, модели, валидаторы и рендеринг}
\column{0.39\textwidth}\textbf{Ключевые принципы}
{\footnotesize\begin{itemize}
\item LiteLLM позволяет обращаться к разным моделям через OpenAI-совместимый API.
\item LLM формирует структурированный вывод по классам доменной модели; код PlantUML она не пишет.
\item Доменная модель описывает архитектуру, функциональные требования и спецификацию API.
\item Рендерер преобразует эту модель в диаграммы; его можно заменить или дополнить, например, Mermaid, без изменения доменной модели.
\end{itemize}}
\end{columns}
\end{frame}

\begin{frame}{Онтология связей между узлами}

\begin{frame}{Реализованные валидаторы диаграммы компонентов}
\textbf{Структура графа}
\begin{itemize}\item У каждого узла уникальный идентификатор.\item Каждая связь соответствует разрешённой паре типов узлов.\item Граф не содержит циклов.\item Каждый узел связан хотя бы с одним другим узлом.\end{itemize}
\end{frame}

\begin{frame}{Реализованные валидаторы диаграммы компонентов}
\textbf{Валидация семантики}
\begin{itemize}\item Брокер сообщений должен быть связан с узлом-производителем и узлом-потребителем сообщений.\item При использовании кэша должен быть определён путь обращения к основному хранилищу при промахе кэша.\end{itemize}
\textbf{Валидация на основе расчётов}
\begin{itemize}\item Рассчитывается загрузка вычислительных узлов с учётом RPS, числа реплик и параллелизма.\item Оцениваются теоретическая задержка обработки и соблюдение заданного бюджета задержки.\end{itemize}
\end{frame}

\begin{frame}{Планируемые валидаторы диаграммы компонентов}
\textbf{Планируемые направления}
\begin{itemize}\item Симуляция нагрузки с помощью SimPy.\item Модели на основе теории массового обслуживания.\item Анализ очередей, задержек и насыщения под нагрузкой.\end{itemize}
\vspace{0.4cm}\textcolor{Muted}{Цель: дополнить статические проверки оценкой поведения модели при заданном профиле нагрузки.}
\end{frame}

\begin{frame}{Реализованные валидаторы диаграмм последовательностей}
\textbf{Текущие правила}
\begin{itemize}\item На каждое функциональное требование — отдельная диаграмма.\item Ссылки на существующие роли и узлы C4.\item Соответствие сценария исходному требованию.\item Использование всех объявленных линий жизни.\item Разные бизнес-роли не используют один клиентский компонент.\item События и уведомления должны быть асинхронными.\end{itemize}

\end{frame}
